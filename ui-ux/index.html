Semantic Integrity: Landmarks & Interactive Controls

dashboard-layout.html

AI defaults to <div> soup because divs are context-free and never throw a validation error. The cost is invisible until someone navigates by landmark regions or the Tab key — then the page has no skeleton at all.

Concept Warm-up · Block vs. Inline

Every HTML element has a default display behavior baked in before any CSS is written. Block-level elements (<div>, <p>, <h1>, <section>, <nav>) always start on a new line, stretch to fill the available width, and accept width/height. Inline elements (<span>, <a>, <strong>) flow inside a line of text, sit side-by-side, and ignore width/height.

<div> is popular with AI precisely because it's the "no-opinion" block element — no semantic meaning, no built-in role. But it is never neutral about layout: dropping a block-level element where an inline one belongs breaks the flow of a sentence, and vice versa. Try it below.

Live demo — wrap the highlighted word

The quarterly report shows that revenue increased 12% year-over-year, driven mostly by the enterprise segment.

<span>: flows inline exactly like plain text — the sentence reads normally around it.

This is exactly why AI's default of wrapping everything in <div> is a double mistake, not a single one: it discards semantic meaning (no landmark, no role) and forces block-level layout onto content that may not want it. Now scale that up from one word to a whole page skeleton:

❌ THE MISTAKE
<div class="page">
  <div class="topbar">
    <div class="logo">Acme</div>
    <div class="links">
      <div class="link" onclick="go('/billing')">Billing</div>
      <div class="link" onclick="go('/team')">Team</div>
    </div>
  </div>

  <div class="content">
    <div class="card">
      <div class="card-title">Invoices</div>
      <div class="btn" onclick="download()">Download</div>
    </div>
  </div>

  <div class="bottom">© 2026 Acme Inc.</div>
</div>
✅ THE MASTER EDITOR FIX
<body class="page">
  <header class="topbar">
    <a class="logo" href="/">Acme</a>
    <nav aria-label="Primary">
      <a class="link" href="/billing">Billing</a>
      <a class="link" href="/team">Team</a>
    </nav>
  </header>

  <main>
    <section class="card" aria-labelledby="inv-h">
      <h2 id="inv-h">Invoices</h2>
      <button type="button" class="btn" onclick="download()">
        Download
      </button>
    </section>
  </main>

  <footer>© 2026 Acme Inc.</footer>
</body>
Technical Rationale

Landmarks are a navigation API, not decoration. Screen reader users jump between <header>, <nav>, <main>, and <footer> with a single keystroke (e.g. NVDA's D key). A div-only page forces a linear, top-to-bottom read of everything.

A div with onclick is not a button. It has no keyboard focus, no Enter/Space activation, no accessible role, and no disabled state — you'd have to hand-roll all four with tabindex and key listeners just to reach parity with the native element that already does it for free.

Accessible Form UX: Label Association & Hit Areas

signup-form.html

AI-generated forms visually look correct — the placeholder sits where a label would — but placeholders vanish on input and are never announced consistently. Add a 24px checkbox meant for a thumb, and the form fails on both the desk and the sidewalk.

❌ THE MISTAKE
<div class="field">
  <input type="email" placeholder="Email address">
</div>

<div class="field">
  <label>Password</label>
  <input type="password">
</div>

<div class="terms">
  <input type="checkbox" id="tos" style="width:14px;height:14px">
  <label for="tos">I agree to the Terms</label>
</div>

<button>Sign up</button>
✅ THE MASTER EDITOR FIX
<div class="field">
  <label for="email">Email address</label>
  <input type="email" id="email" name="email"
         autocomplete="email" required>
</div>

<div class="field">
  <label for="pw">Password</label>
  <input type="password" id="pw" name="password"
         autocomplete="new-password"
         aria-describedby="pw-hint" required>
  <p id="pw-hint" class="hint">Min. 8 characters</p>
</div>

<label class="terms">
  <input type="checkbox" id="tos" class="tos-input">
  <span>I agree to the Terms</span>
</label>

<button type="submit">Sign up</button>

<style>
  /* Visual box stays 14px; tappable area meets 44px minimum */
  .terms{ display:flex; align-items:center; gap:10px;
          padding:15px 0; min-height:44px; cursor:pointer; }
  .tos-input{ width:14px; height:14px; flex-shrink:0; }
</style>
Technical Rationale

Placeholders are not labels. They disappear the moment a user types, have no reliably announced role across screen readers, and fail WCAG 3.3.2 (Labels or Instructions). Every input needs a persistent, programmatically-associated <label for="">.

Hit area ≠ visual size. WCAG 2.5.8 and Apple/Google HIG both target a 44×44px minimum touch target. Wrapping the checkbox and its text in one <label> with generous padding gets you the full tap area without inflating the checkbox graphic itself.

CSS Architecture: Don't Let BEM and Tailwind Marry

pricing-card.html

AI happily bolts a dozen Tailwind utilities onto a BEM-named element because both "worked" in training data it saw separately. The result: two conflicting sources of truth for the same box, and a specificity fight the next developer has to debug blind.

❌ THE MISTAKE — Spaghetti Hybrid
<div class="pricing-card__header flex items-center
            justify-between p-4 bg-white rounded-lg
            pricing-card__header--highlighted">
  <h3 class="pricing-card__title text-xl font-bold">Pro</h3>
</div>

<style>
.pricing-card__header{ display:flex; padding:20px; background:#fff; }
.pricing-card__header--highlighted{ background:#f5f5ff; }
.pricing-card__title{ font-size:22px; font-weight:800; }
</style>
<!-- Which wins: the 4px Tailwind padding or the 20px BEM padding?
     Depends on stylesheet load order. Nobody on the team can say
     without opening devtools. -->
✅ THE MASTER EDITOR FIX — Pick One System
<!-- Option A: Tailwind-only (utility-first project) -->
<div class="flex items-center justify-between p-5
            bg-indigo-50 rounded-lg">
  <h3 class="text-xl font-extrabold">Pro</h3>
</div>

<!-- Option B: BEM-only (design-system / component project) -->
<div class="pricing-card__header pricing-card__header--highlighted">
  <h3 class="pricing-card__title">Pro</h3>
</div>
<style>
.pricing-card__header{ display:flex; align-items:center;
  justify-content:space-between; padding:20px; background:#fff;
  border-radius:8px; }
.pricing-card__header--highlighted{ background:#eef2ff; }
.pricing-card__title{ font-size:22px; font-weight:800; }
</style>
Technical Rationale

BEM and Tailwind solve the same problem two incompatible ways: BEM centralizes style decisions in a stylesheet with a naming contract; Tailwind decentralizes them into the markup itself. Mixed together, both a class-based rule and a utility class can target padding on the same element — the winner is decided by CSS cascade order and specificity, not by the developer who wrote either line.

The fix is architectural, not cosmetic: declare one system per project (or per component boundary if migrating) in your styleguide, and enforce it with a linter (e.g. eslint-plugin-tailwindcss or a Stylelint BEM plugin) so the mistake can't reappear in review.

Fluid Typography & "Liquid Thinking"

article-header.css

AI reaches for a pixel value because it's the most common token in its training data. That value never respects the user's browser font-size setting, and never adapts between a 320px phone and a 2560px monitor without a wall of media queries.

Concept Ladder · From Fixed Pixels to clamp()

Six units, one evolving answer to "how big should this text be." Each stage below fixes one problem in the previous stage — and introduces a new one, until clamp() closes the loop.

Stage 1
px
Absolute. Same size everywhere, forever — including when a user sets a larger default font size for readability.
✗ Ignores user prefs
Stage 2
%
Relative to the parent's font size. Better in theory — but the "parent" changes per component, so the same % renders differently everywhere it's used.
△ Inconsistent
Stage 3
em
Relative to the immediate parent, same as %, but composable for spacing. The catch: nest it and each level multiplies the last. Try the demo below.
✗ Compounds silently
Stage 4
rem
Relative to the root (<html>) only — never compounds, and scales when a user changes their browser's base font size.
✓ Respects user prefs
Stage 5
vw
Relative to viewport width — truly fluid across screen sizes, but unbounded: too small on a phone, absurdly large on an ultrawide.
✗ No min or max
Stage 6
clamp()
clamp(min, vw-value, max) — fluid like vw, bounded like rem. One rule, no breakpoints.
✓ Fluid + bounded
Live demo — the em compounding trap (Stage 3)
Depth 0 · effective size 16.0px
Notification badge

Each click wraps the badge in one more parent styled font-size: 1.2em — exactly what a design system's nested Card > Section > Badge components tend to do by accident. No single line of CSS looks wrong; the bug is in the accumulation.

Live demo — drag to simulate device width (Stages 1, 5 & 6)
📱 🖥️ 380px viewport
px Fixed 32px heading
vw only Unbounded 8vw heading
clamp() clamp(1.5rem, 8vw, 2.75rem)

At 320px, vw only shrinks toward unreadable; drag past ~900px and it balloons past any sane heading size. clamp() tracks the same fluid curve in the middle but locks to its min/max at the extremes — that's the row that stays readable at both ends of the slider.

That's the theory and the failure modes. Here's the same lesson as a code diff you can paste directly into a component:

❌ THE MISTAKE — Fixed Pixels
.article-title{
  font-size: 42px;
}
.article-body{
  font-size: 16px;
}

/* Then patched with breakpoints as complaints come in */
@media (max-width: 600px){
  .article-title{ font-size: 26px; }
}
@media (max-width: 400px){
  .article-title{ font-size: 21px; }
}
✅ THE MASTER EDITOR FIX — clamp() Scale
html{
  font-size: 100%; /* respects user/browser base size */
}

.article-title{
  /* clamp(min, preferred-viewport-relative, max) */
  font-size: clamp(1.5rem, 1rem + 2.5vw, 2.75rem);
  line-height: 1.15;
}
.article-body{
  font-size: clamp(1rem, 0.95rem + 0.2vw, 1.125rem);
  line-height: 1.6;
}
/* One rule. Scales continuously from 320px to 2560px.
   No breakpoint patchwork, no jump cuts. */
Technical Rationale

Pixels are absolute and deaf to user preference. A user who bumps their OS/browser default font size for readability sees zero change on a px-sized site — that's a WCAG 1.4.4 (Resize Text) failure. rem units at least scale with the root font size.

clamp() is "liquid thinking" in one line: the middle argument (a vw-based fluid value) scales continuously with viewport width, while the min/max rem bounds guarantee text never becomes unreadably small or absurdly large — replacing 3–5 breakpoint overrides with a single, mathematically smooth rule.

JS Clean Code: Refactoring the "God Function"

checkout-form.js

AI tends to solve a feature request with one function that does everything requested, in the order requested. It runs on the happy path — but validation, state mutation, and DOM writes are now welded together and untestable in isolation.

❌ THE MISTAKE — One Function, Every Job
function handleSubmit(e) {
  e.preventDefault();
  const email = document.getElementById('email').value;
  const card = document.getElementById('card').value;
  let errors = [];

  if (!email.includes('@')) errors.push('Bad email');
  if (card.length !== 16) errors.push('Bad card number');

  if (errors.length > 0) {
    document.getElementById('errors').innerText = errors.join(', ');
    document.getElementById('errors').style.display = 'block';
    return;
  }

  window.appState.email = email;
  window.appState.card = card;
  window.appState.step = 'confirm';

  document.getElementById('form-step').style.display = 'none';
  document.getElementById('confirm-step').style.display = 'block';
  document.getElementById('confirm-email').innerText = email;
}
✅ THE MASTER EDITOR FIX — One Job per Function
// 1. Pure validation — no DOM, no state, fully unit-testable
function validateCheckout({ email, cardNumber }) {
  const errors = [];
  if (!email.includes('@')) errors.push('Bad email');
  if (cardNumber.length !== 16) errors.push('Bad card number');
  return errors;
}

// 2. State transition — no DOM
function advanceToConfirm(state, { email, cardNumber }) {
  return { ...state, email, cardNumber, step: 'confirm' };
}

// 3. Rendering — reads state, writes DOM, nothing else
function renderConfirmStep(state) {
  document.getElementById('form-step').style.display = 'none';
  document.getElementById('confirm-step').style.display = 'block';
  document.getElementById('confirm-email').innerText = state.email;
}

function renderErrors(errors) {
  const el = document.getElementById('errors');
  el.innerText = errors.join(', ');
  el.style.display = errors.length ? 'block' : 'none';
}

// 4. Orchestrator — coordinates, does no work itself
function handleSubmit(e) {
  e.preventDefault();
  const input = {
    email: document.getElementById('email').value,
    cardNumber: document.getElementById('card').value,
  };

  const errors = validateCheckout(input);
  if (errors.length) return renderErrors(errors);

  appState = advanceToConfirm(appState, input);
  renderConfirmStep(appState);
}
Technical Rationale

Single Responsibility Principle isn't academic here — it's testability. validateCheckout can be unit-tested with plain objects and zero DOM mocking. In the "mistake" version, testing validation means booting a whole document and stubbing five DOM elements first.

Decoupled state from rendering also kills a class of bugs: when state mutation and UI-write are the same step, a failed render can leave state and screen out of sync. Separated, advanceToConfirm is deterministic and replayable regardless of what the DOM is doing.

Naming & Searchability: Kill the Mental Map

order-utils.js

Short variable names feel efficient while writing the code, but they force every future reader to build a private decoder ring — "d is the discount, u is the user, right?" — and make the codebase impossible to grep.

❌ THE MISTAKE — Mental Mapping
function calc(u, o, d) {
  let t = 0;
  for (let i = 0; i < o.length; i++) {
    const it = o[i];
    let p = it.p * it.q;
    if (d && it.c) p = p * (1 - d);
    t += p;
  }
  if (u.vip) t = t * 0.95;
  return t;
}

// grep "amount" or "total" in this file → zero hits.
// New engineer has to read every line to know what "t" means.
✅ THE MASTER EDITOR FIX — Explicit, Searchable
function calculateOrderTotal(user, orderItems, discountRate) {
  let runningTotal = 0;

  for (const item of orderItems) {
    let lineTotal = item.unitPrice * item.quantity;

    const itemIsDiscountEligible = discountRate && item.isCouponEligible;
    if (itemIsDiscountEligible) {
      lineTotal = lineTotal * (1 - discountRate);
    }
    runningTotal += lineTotal;
  }

  const VIP_DISCOUNT_MULTIPLIER = 0.95;
  if (user.isVip) {
    runningTotal *= VIP_DISCOUNT_MULTIPLIER;
  }

  return runningTotal;
}

// grep "runningTotal" instantly surfaces every relevant line.
Technical Rationale

"Searchability" is a named clean-code heuristic (Robert C. Martin): a name should be greppable across the codebase. t and d match thousands of unrelated tokens; runningTotal and discountRate match exactly the concept you're looking for.

Magic numbers get named too — VIP_DISCOUNT_MULTIPLIER instead of a bare 0.95 means the next engineer doesn't have to reverse-engineer business intent from an arithmetic literal, and the value has exactly one place to change.

Error Handling: Spotting the "Silent Killer"

fetch-profile.js

AI-generated try/catch blocks are frequently decorative: they satisfy a syntax requirement without doing anything when an error actually occurs. The app "works" in the demo and fails invisibly in production — no log, no user feedback, no stack trace.

❌ THE MISTAKE — Empty Catch, Ignored Rejection
async function loadProfile(userId) {
  try {
    const res = await fetch(`/api/users/${userId}`);
    const data = await res.json();
    renderProfile(data);
  } catch (e) {
    // TODO: handle error
  }
}

// Fire-and-forget call elsewhere in the app —
// a rejected promise here just vanishes.
loadProfile(currentUser.id);
✅ THE MASTER EDITOR FIX — Handled, Logged, Surfaced
async function loadProfile(userId) {
  try {
    const res = await fetch(`/api/users/${userId}`);
    if (!res.ok) {
      throw new Error(`Profile request failed: ${res.status}`);
    }
    const data = await res.json();
    renderProfile(data);
  } catch (error) {
    console.error('loadProfile failed', { userId, error });
    reportToErrorTracker(error);
    renderProfileError('We couldn\'t load this profile. Try again.');
  }
}

// Every call site handles the returned promise explicitly
loadProfile(currentUser.id).catch((error) => {
  console.error('Unhandled loadProfile rejection', error);
});
Technical Rationale

An empty catch block is worse than no try/catch at all — it actively suppresses the stack trace and error signal that would have surfaced the bug in monitoring, console, or a crash report. fetch() also doesn't reject on HTTP 4xx/5xx by default, so res.ok must be checked explicitly or failures silently render nothing.

Every promise needs an owner. A "fire-and-forget" async call with no .catch() and no await in a try/catch produces an unhandled promise rejection — in Node this can crash the process; in the browser it's a silent console warning almost nobody reads in production.

Requirements Stress-Testing: The Simulator Pattern

user-journey.md

AI builds exactly the flow described in the ticket, in the happy-path order it was described. It won't notice the ticket has a logic gap unless you explicitly force it to role-play the journey end-to-end before writing code — that's the "Requirements Simulator" prompt pattern.

❌ THE MISTAKE — Ticket Taken at Face Value
TICKET: "Add a 'Cancel Subscription' button to account
settings. On click, cancel the subscription and show a
confirmation message."

AI OUTPUT: Ships exactly that. One button, one click,
one toast: "Subscription cancelled." Done.

--- Gap discovered in production ---
A user with 3 team seats and an annual plan (11 months
prepaid, non-refundable) clicks Cancel. They lose access
immediately, get no prorated refund messaging, and their
whole team is logged out mid-workday with zero warning.
Support ticket volume spikes the same afternoon.
✅ THE MASTER EDITOR FIX — Simulate the Journey First
PROMPT ADDED BEFORE ANY CODE:
"Before implementing, simulate this user journey step by
step as three different personas: (1) a monthly single-seat
user, (2) an annual multi-seat team admin, (3) a user
mid-way through a free trial. At each step, state what they
see, what data changes, and flag any decision the ticket
does NOT specify."

SIMULATION SURFACES THE GAP:
- Team admin persona → "What happens to the other 2 seats?
  Ticket doesn't say. Do they lose access instantly or at
  period end?"
- Annual persona → "Is there a refund? Ticket doesn't say."
- Trial persona → "Is 'cancel' the same action as 'end
  trial early'? Ticket conflates them."

RESULT: Ticket goes back to product with 3 concrete open
questions BEFORE a single line of code is written.
Technical Rationale

AI executes literally; it doesn't interrogate a spec unless asked to. The "Requirements Simulator Pattern" means prompting the model to walk through the feature as multiple real personas before generating code, explicitly asking it to flag anything the ticket leaves ambiguous.

This catches logic gaps at the cheapest possible point — before implementation — instead of in a post-incident review after a support escalation, which is dramatically more expensive to fix in code, comms, and trust.

Inclusive Prompting for Design Imagery

hero-imagery.prompt

A generic image prompt inherits whatever bias is most statistically common in the model's training distribution — often a narrow age range, body type, ability, and ethnicity. Naming the representation you want is a design decision, not an afterthought.

❌ THE MISTAKE — Generic Prompt
PROMPT:
"A professional using our project management app on a
laptop in a modern office, hero image for landing page."

TYPICAL RESULT:
Defaults toward a single narrow archetype — one age range,
one body type, one ethnicity, able-bodied, in a glossy
tech-startup office. Run 10 times, you'll get 10 near-
identical people and settings.
✅ THE MASTER EDITOR FIX — Explicit Representation
PROMPT:
"A set of 4 hero images for a project management app
landing page, each showing a different professional using
the app on a laptop or tablet. Vary across the set:
- Age range spanning early-career to senior (20s–60s)
- Body types and physical abilities, including one person
  using a wheelchair at a standing desk
- Skin tones and ethnic backgrounds across the set
- Work settings: a home office, a co-working space, a
  small retail back-office, a remote outdoor site visit
- Gender presentation across the set
Avoid stock-photo clichés (forced smiles, thumbs-up,
posed laptop angles). Show natural, task-focused posture."

RESULT: A set that actually reflects who uses the product,
specified as concrete, checkable art-direction constraints
rather than a single vague adjective like "diverse."
Technical Rationale

"Diverse" alone is not an actionable brief. A single vague adjective gives the model nothing concrete to satisfy and often gets tokenistically ignored. Naming specific axes — age, ability, body type, setting, and asking for variation across a set rather than in one image — gives the model checkable constraints.

This is UX work, not just image-generation etiquette: representation in hero imagery directly affects whether a prospective user in the shown-underrepresented group can picture themselves as a customer — a measurable driver of conversion and trust for a broader audience.

ARIA Hallucinations: Attributes That Don't Exist (or Shouldn't)

modal.html

AI has seen thousands of ARIA attributes in training and sometimes blends them — misspelling one, or applying a real one to the wrong element. Both look plausible in a code review and both break assistive tech in ways a sighted visual QA pass will never catch.

❌ THE MISTAKE — Hallucinated / Misapplied ARIA
<div class="modal" role="dialog"
     aria-labeledby="modal-title">
  <!-- "aria-labeledby" doesn't exist — correct attribute is
       "aria-labelledby" (two L's). Screen readers silently
       ignore the misspelled one; the dialog announces with
       no accessible name at all. -->

  <h2 id="modal-title">Delete this file?</h2>

  <button class="close-x" aria-hidden="true">
    ×
  </button>
  <!-- aria-hidden="true" on a focusable, clickable button
       hides it from the accessibility tree entirely — it's
       still Tab-reachable and clickable, but a screen reader
       user gets a mysterious, unlabeled focus stop that
       does nothing when activated. -->
</div>
✅ THE MASTER EDITOR FIX — Verified, Correct ARIA
<div class="modal" role="dialog"
     aria-modal="true"
     aria-labelledby="modal-title">

  <h2 id="modal-title">Delete this file?</h2>

  <button class="close-x" aria-label="Close dialog">
    ×
  </button>
  <!-- Focusable + interactive → never aria-hidden.
       aria-label supplies an accessible name for the
       icon-only button instead. -->
</div>
Technical Rationale

ARIA attribute names are not spell-checked by the browser. An invalid attribute like aria-labeledby is simply ignored by the accessibility tree — no console warning, no visual difference, and the element quietly loses its accessible name. Validate against the actual ARIA spec, or run an automated audit (axe DevTools) that flags unrecognized attributes.

The first rule of aria-hidden: never on a focusable element. Per the WAI-ARIA spec itself, aria-hidden="true" must not be set on an element that (or whose descendant) can receive focus, because it creates exactly this "hidden but reachable" trap for keyboard and screen-reader users.

Accessibility Overlays: The Shortcut That Isn't

audit-strategy.md

A one-line overlay script is the "AI-generated fix" of accessibility — it looks like compliance was achieved with near-zero effort. It patches surface symptoms in the DOM at runtime and leaves the actual structural defects in your source untouched.

❌ THE MISTAKE — Overlay "Shortcut"
<!-- One script tag, marketed as instant WCAG compliance -->
<script src="https://widget.accessibility-overlay.example/embed.js"
        data-account="12345"></script>

<!-- What it actually does:
     - Injects a floating toolbar (font size, contrast toggle)
     - Attempts to auto-generate alt text and ARIA labels via
       pattern-matching AFTER the page has already loaded
     - Cannot fix: illogical heading order, broken keyboard
       traps, non-semantic custom widgets, focus management
       in JS-driven modals, or actual content meaning
     - Source HTML shipped to every user is UNCHANGED -->
✅ THE MASTER EDITOR FIX — Manual, Source-Level Audit
AUDIT WORKFLOW (repeatable, added to Definition of Done):

1. Automated pass — axe-core / Lighthouse in CI on every PR
   → catches ~30-40% of issues: missing alt, contrast ratios,
     duplicate IDs, invalid ARIA.

2. Keyboard-only pass — unplug the mouse. Tab through every
   interactive element on the page. Can you reach it, see
   focus, and activate it with Enter/Space?

3. Screen reader pass — VoiceOver (Mac) or NVDA (Windows) on
   real user flows, not just the homepage: complete the
   checkout, not just "look at" the checkout.

4. Fix in source — every finding becomes a code change in the
   actual component (correct heading order, real <button>,
   proper labelledby) — not a runtime patch layered on top.
Technical Rationale

Overlays operate on the rendered DOM after the fact, and by pattern-matching — they cannot understand the actual meaning of a custom widget, cannot repair broken focus order in a JS framework's virtual DOM, and multiple documented lawsuits and disability-advocacy statements (including the "Overlay Fact Sheet" signed by hundreds of accessibility professionals) point to overlays as a source of new usability problems, not a fix.

A manual audit produces source-level fixes that compound: once a component's heading structure or focus trap is corrected in code, it's fixed for every page that reuses it — an overlay's patch has to re-run, and re-guess, on every page load, for every user, forever.

Mobile-First Layout: Same Markup, Two Experiences

responsive-dashboard.html

AI frequently designs the desktop screenshot it was shown, then bolts on a hamburger menu and a couple of max-width overrides to "make it responsive." Mobile-first flips the build order: write the constrained, single-column case as the default, then progressively add layout as space becomes available. Drag the slider — this is one component, one stylesheet, no JS layout logic.

Below ~600px the hamburger takes over and the sidebar becomes a horizontal scroll-tab strip — the mobile default. Past ~1000px, the same markup gets a persistent sidebar, a horizontal nav, and a 3-column grid — all min-width additions layered on top, never a mobile feature removed.

❌ THE MISTAKE — Desktop-First, Torn Down
.sidebar{
  width: 240px;
  display: block;
}
.content{
  display: grid;
  grid-template-columns: repeat(3, 1fr);
}

/* Mobile is an afterthought — override everything back down */
@media (max-width: 600px){
  .sidebar{ display: none; }
  .content{ grid-template-columns: 1fr; }
  .mobile-menu-button{ display: block; } /* wasn't planned for */
}
✅ THE MASTER EDITOR FIX — Mobile-First, Built Up
/* Base styles ARE the mobile styles — no query needed */
.sidebar{ display: flex; overflow-x: auto; }
.content{ display: grid; grid-template-columns: 1fr; }

/* Progressively ADD capability as space becomes available */
@media (min-width: 600px){
  .content{ grid-template-columns: repeat(2, 1fr); }
}
@media (min-width: 1000px){
  .sidebar{ flex-direction: column; width: 240px; }
  .content{ grid-template-columns: repeat(3, 1fr); }
}
Technical Rationale

Mobile-first isn't a screen-size preference — it's a load-order and complexity discipline. A constrained, single-column layout has fewer failure modes than a 3-column desktop grid, so building it first means every subsequent min-width query only ever adds capability, never fights a rule it has to un-do.

Desktop-first breaks down under real content and real devices: max-width overrides accumulate as more breakpoints are discovered in QA, and specificity fights between the base rule and its override get harder to trace with every added query — exactly the CSS Architecture spaghetti from Topic 03, at the layout level.

Design for Every State, Not Just the Happy Path

revenue-card.jsx

A ticket that says "show a card with revenue data" gets you exactly one screen from AI: the one with data in it. It rarely generates what the same card looks like while the request is in flight, when there's genuinely nothing to show yet, or when the request fails — so those get invented under deadline pressure, inconsistently, per-component.

Live demo — same card, four states

Only one of these four was in the original ticket. The other three were the actual UX design work — and they're exactly the states real users hit most: a slow connection, a brand-new account with no data yet, and a flaky API.

The four-state checklist — ask this for every screen before calling a design "done": what does it look like while loading, when it's genuinely empty, when the request errors, and only then, what it looks like on success.
